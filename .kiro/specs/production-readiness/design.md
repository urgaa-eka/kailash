# Design Document

## Overview

This design turns nine requirements into one coherent mechanism: a small set of Python verification checks that run identically on a developer machine, in CI, and on the VPS; two categories of written record that those checks generate rather than transcribe; and a deployment topology where production is reachable only through staging.

The central design decision is that **every acceptance criterion expressed as "SHALL exit with code 0 only when…" becomes a check, not a convention.** Conventions drift. The Firebase project identifier defect that prompted Requirement 3 was a convention failure: four files were meant to agree and one was missed. A check that reads all four and compares them cannot be missed.

The second decision is that **Requirement 1 is a diagnosis, not a fix.** The requirement explicitly forbids presuming a root cause, and the evidence supports that caution. Section 1 below specifies a procedure and a decision tree, and labels every candidate explanation as a hypothesis to be tested. No remediation is designed for a cause not yet established.

### Language and runtime

All new verification code is **Python 3.11**, matching the backend and CI runners. Reasoning:

- `pytest` 8.4.2 is already in `backend/requirements.txt` and CI already runs it in three jobs.
- Python runs natively on the developer's Windows host. The existing `scripts/health_check.sh` does not, and `scripts/generate_services.ps1` does not run on the Linux CI runners or the VPS. Bash would make every check unrunnable locally; PowerShell would make every check unrunnable in CI. Python is the only option that runs in all three places.
- The checks must not depend on `yarn`, `node`, or `docker` being present in order to *load*, so that a missing prerequisite is reported as a distinct exit code rather than a crash.

Code examples below are Python and YAML.

### What this design does not change

Application behaviour is out of scope. The only backend source change designed here is an additive `commit` field on the health response, required by Requirement 6.6. No route logic, no UI, no data model.

## Architecture

```
scripts/verify/                        ← all checks, one Python package
  common.py          exit-code contract, Finding/Report, git file enumeration
  health_diagnose.py    R1   collect + classify container health evidence
  deployment_check.py   R2, R8.6   HTTP + TLS + asset-manifest verification
  config_drift.py       R3   cross-file value agreement
  secret_scan.py        R4   credential detection in tracked files
  build_audit.py        R5   build-context path resolution
  rollback.py           R6   rollback precondition checks
  orphan_review.py      R7   Docker host accountability
  repo_state.py         R9   working-tree and repository-identity gates
  workflow_gate.py      R2.6, R3.4/3.6, R4.4, R8.4/8.5/8.7/8.8  workflow graph
  data/
    project_map.json        Firebase project id → project number
    retained_containers.json  Cleanup_Record source of truth
    denylist.txt            known-compromised literal credentials

docs/records/                          ← generated evidence, dated
  container-health-diagnosis.md   Diagnosis_Record          (R1)
  container-health-evidence.json  raw docker inspect capture (R1)
  docker-host-cleanup.md          Cleanup_Record            (R7)
  rollback-rehearsal.md           rehearsal timings         (R6.7)

docs/runbooks/                         ← procedures, hand-written
  rollback.md                     Rollback_Procedure        (R6.1)
  staging.md                      staging operations        (R8)

tests/verify/                          ← tests for the checks themselves
```

Records live under `docs/records/` and procedures under `docs/runbooks/`. The split matters: a record is dated evidence that ages and is superseded, a runbook is a procedure an operator follows under pressure. Mixing them means an operator scrolling for a rollback command reads a stale diagnosis instead.

Every record that a check can generate **is** generated by that check via `--emit-record`, from a machine-readable source. Hand-maintained records diverge from the systems they describe — the same defect class as Requirement 3, one level up.

### The exit-code contract

Uniform across all checks. Requirements only distinguish zero from non-zero, so the finer grades are free.

| Code | Meaning |
| --- | --- |
| 0 | Every rule passed. |
| 1 | At least one rule found a real defect. |
| 2 | The check could not run: missing prerequisite, unreachable daemon, no network where required. |
| 3 | Invalid invocation. |

Separating 2 from 1 is load-bearing in CI. A runner without a Docker socket must not be reported as a configuration defect, or the checks get muted the first time infrastructure hiccups.

### Shared contract

```python
# scripts/verify/common.py
from dataclasses import dataclass, field
from enum import IntEnum
from pathlib import Path

class Exit(IntEnum):
    OK = 0
    FAILED = 1
    UNAVAILABLE = 2
    USAGE = 3

@dataclass(frozen=True)
class Finding:
    rule: str                      # stable id, e.g. "config-drift.firebase-project-id"
    path: str | None = None        # file path or endpoint URL
    line: int | None = None        # 1-based, when a file location is known
    observed: str | None = None    # the value actually found
    expected: str | None = None    # the value required, when singular
    message: str = ""

@dataclass
class Report:
    check: str
    findings: list[Finding] = field(default_factory=list)
    suppressions: list[Finding] = field(default_factory=list)
    unavailable: str | None = None   # set when a prerequisite is absent

    def exit_code(self) -> Exit:
        if self.unavailable:
            return Exit.UNAVAILABLE
        return Exit.FAILED if self.findings else Exit.OK
```

Every check exposes the same CLI surface:

```
python -m scripts.verify.<name> [--root PATH] [--json] [--emit-record PATH]
```

`--root` is not cosmetic. It is the reason the checks are testable: a test constructs a synthetic repository in a temporary directory and points the check at it. A check that hard-codes the repository root can only ever be tested against the one input that already passes. Every check therefore resolves all paths relative to `--root`, defaulting to the git top level.

Output is one line per finding, machine-greppable and human-readable:

```
FAIL config-drift.firebase-project-id frontend/.env.production:12 observed=kailash-15365 expected=kailash-38268
```

This single format satisfies the printing obligations of 2.7, 3.7, 4.7, 5.5, 6.8 and 7.6 at once.

## Component 1: Container Health Diagnosis (Requirement 1)

### The signal that shapes the procedure

Fifteen containers. Fourteen report `unhealthy`. The one that does not is `frontend`.

`frontend/Dockerfile` declares no `HEALTHCHECK` and the compose `frontend` service declares no `healthcheck` block. So `frontend` is not healthier than the others — **it is the only container with no health probe at all.** Restated: every container that has a probe is failing it, and the only container that is not failing is the one with nothing to fail.

That reframes the question. Fourteen independent probe bugs across five different probe mechanisms (compose `curl`, compose `mongosh`, compose `pg_isready`, compose `redis-cli`, image-level `python urllib`) would be a remarkable coincidence. A uniform failure across heterogeneous probes points first at something common to all of them. The procedure therefore tests common causes **before** per-container causes, because the per-container path costs fourteen investigations and the common-cause path costs five probes.

This is an observation about the shape of the evidence, not a conclusion about the cause.

### Where each probe actually comes from

Establishing this first matters, because two of the three service classes are probed by a definition that is not in `docker-compose.yml`.

| Container class | Probe declared in | Probe |
| --- | --- | --- |
| `backend` | `docker-compose.yml` | `curl -f http://localhost:8000/api/health`, 30s/10s/3/40s |
| 9 Platform_Services | **image**, via `backend/services/Dockerfile.service` | `python -c` `urllib.request.urlopen(f'http://localhost:{os.environ["PORT"]}/health')`, 30s/5s/5, no start period |
| `company` | `docker-compose.yml` | `python -c` urllib against `:8110/health`, 30s/10s/3/20s |
| `mongo` | `docker-compose.yml` | `mongosh --quiet --eval "db.adminCommand('ping')"`, 30s/**20s**/5/60s |
| `postgres` | `docker-compose.yml` | `pg_isready -U kailash`, 30s/10s/3, **no start period** |
| `redis` | `docker-compose.yml` | `redis-cli -a "${REDIS_PASSWORD:-…}" ping`, 30s/10s/3, **no start period** |
| `frontend` | nowhere | none |

The `x-platform-service` YAML anchor declares no `healthcheck`, which initially reads as "the platform services have no probe". They do — it is baked into the image by `Dockerfile.service`. The effective probe is therefore only visible through `docker inspect --format '{{json .Config.Healthcheck}}'`, and the procedure reads it from there rather than from the compose file. Reading the compose file alone would have investigated the wrong probe for nine of the fourteen containers.

### Hypotheses to test

Explicitly hypotheses. Each has a probe that confirms or eliminates it. None is assumed.

| # | Hypothesis | Probe | Prior |
| --- | --- | --- | --- |
| H1 | Host resource saturation makes every probe exceed its timeout simultaneously | `docker stats --no-stream`, `docker info` memory ceiling, measure each probe's wall time | **Leading.** The only hypothesis that explains a uniform failure across heterogeneous probes without coincidence. |
| H2 | `redis` probe authenticates with an empty password because `REDIS_PASSWORD` is unset in the shell that ran compose, so `${REDIS_PASSWORD:-…}` renders the fallback — or the fallback and the running server disagree | `docker compose --profile kailash-ai config` and read the rendered `test` string; replay it inside the container | Plausible, `redis` only. |
| H3 | `mongosh` startup exceeds its 20s timeout on a loaded host | Time `docker exec kailash-mongo mongosh --quiet --eval "db.adminCommand('ping')"` | Plausible. The compose comment already records that 10s was too tight, so this probe has a history of timing out. |
| H4 | `postgres` and `redis` have no `start_period`, so a slow first boot marks them unhealthy at ~90s and `restart: unless-stopped` never clears it | Read `FailingStreak` and the first `Log` entry timestamps from `docker inspect` | Plausible for the initial transition; does not explain a 5-hour-old container still failing. |
| H5 | `backend` serves its health route at a path other than `/api/health`, so `curl -f` gets a 404 | `docker exec kailash-backend curl -s localhost:8000/openapi.json` and read the actual path list | Plausible, `backend` only. `backend/shared/build_app()` mounts `/health`; a repository-wide grep for a literal health route in `backend/**/*.py` matches nothing, so the route is registered indirectly and its final path must be read from the running app rather than inferred. |
| H6 | Platform services are not listening, so the probe gets connection-refused | Replay the probe; a `ConnectionRefusedError` traceback distinguishes this from an HTTP error | Plausible. Would indicate an application startup defect, not a probe defect. |
| H7 | Platform-service probes fail on a non-200 response | Replay the probe and read the exception type | Plausible. `urllib.request.urlopen` raises `HTTPError` on any non-2xx, so a 404 or 503 exits non-zero via traceback rather than the `sys.exit(1)` branch. The recorded `Output` will therefore contain a Python traceback whose exception class **is** the diagnosis. |
| H8 | `mongosh` is absent from the image | `docker exec kailash-mongo which mongosh` | Weak. `mongo:7` ships `mongosh`. Tested anyway because Requirement 1.2 requires the evidence for all 15. |
| H9 | Clock skew in the Docker VM after host sleep distorts interval and timeout arithmetic | Compare `docker run --rm alpine date` to host time | Weak but cheap, and it would explain a uniform failure. |

H1 and H9 are the only hypotheses that explain the uniform pattern by themselves. H2, H3, H5, H6, H7 explain subsets. The procedure runs the cheap uniform-cause probes first.

### Procedure

**Phase A — capture.** For each of the 15 containers:

```python
CAPTURE = {
    "health":      "docker inspect --format '{{json .State.Health}}' {name}",
    "effective":   "docker inspect --format '{{json .Config.Healthcheck}}' {name}",
    "state":       "docker inspect --format '{{json .State}}' {name}",
    "restarts":    "docker inspect --format '{{.RestartCount}}' {name}",
}
```

Written verbatim to `docs/records/container-health-evidence.json`. The raw capture is preserved separately from the narrative record so a reviewer can check the narrative against the evidence. `.State.Health.Log` retains the last five probe attempts with `Start`, `End`, `ExitCode` and `Output` — this is the primary evidence Requirement 1.1 demands, and `End - Start` per attempt is the measurement Requirement 1.6 needs.

**Phase B — uniform-cause probes.** Run once for the whole host, not per container: H1, H9, then the rendered-config read for H2. If H1 confirms, stop and remediate the host before touching any probe definition; re-running Phase A on an unsaturated host may resolve most of the fourteen and would make fourteen definition edits unnecessary.

**Phase C — per-container replay.** Only for containers still failing after Phase B. For each, extract the effective probe from `.Config.Healthcheck.Test`, replay it via `docker exec`, and record exit code, stdout, stderr and wall time. The replay is the decisive step because it separates three outcomes that `unhealthy` alone conflates:

- replay succeeds → the service is fine and the *probe invocation* is at fault (timeout, interpolation, CMD form)
- replay fails with connection-refused → the service is not listening
- replay fails with an HTTP status → the service is listening and rejecting the probed path

**Phase D — Requirement 1.2 evidence.** For all 15 containers, `docker exec <c> which <exe>` where `<exe>` is the executable extracted from the effective probe. Recorded for every container including those already passing, because 1.2 is a claim about all fifteen.

### Decision tree

| Finding | Conclusion | Action | Criterion |
| --- | --- | --- | --- |
| `which` exits non-zero | Probe names an executable absent from the image | Replace with an executable the image has | 1.2 |
| Replay succeeds, recorded probe fails | Probe invocation, not the service | Raise `timeout` to 3× measured, add `start_period` ≥ measured first-success time | 1.6 |
| Replay succeeds, host saturated | Environmental | Record blocking condition, remediate host, re-measure | 1.8 |
| Replay returns 200 on a different path than probed | Path mismatch | Align probe to the served path, or add the route | 1.7 |
| Replay returns non-200 on the probed path | Service rejecting the probe | Application defect; record blocking condition | 1.8 |
| Replay refused | Service not listening | Application defect; record blocking condition | 1.8 |
| Rendered probe string differs from intent | Compose interpolation | Correct the reference | 1.7 |

Requirement 1.7 is the case worth naming: a container that answers 200 on its health path while Docker calls it unhealthy is *definitionally* a probe defect, and the record must say which element of the definition failed rather than leaving it as "unhealthy".

### Two changes the requirements force regardless of diagnosis

**`frontend` must gain a probe.** Requirement 1.5 requires all 15 containers to report `healthy`. A container with no `HEALTHCHECK` never reports `healthy` — it reports no health state at all, so `docker ps --filter health=healthy` will list at most 14 names and 1.5 cannot be met. `nginx:alpine` has no `curl`; it has BusyBox `wget`. Subject to Phase D confirming `which wget`:

```yaml
healthcheck:
  test: ["CMD", "wget", "--quiet", "--tries=1", "--spider", "http://localhost/"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 10s
```

An HTTP probe is preferred over `nginx -t` because `nginx -t` validates configuration syntax without proving the server answers requests.

**`/api/health` is the contract.** Requirement 1.3 fixes the path. If H5 confirms the app does not serve it, the route is added rather than the probe retargeted — three other requirements (2.3, 4.6, 6.6) and both deploy scripts already depend on `/api/health`, so it is the more entrenched of the two paths.

### Diagnosis_Record

`docs/records/container-health-diagnosis.md`, generated by `health_diagnose.py --emit-record`. One section per container:

```markdown
### kailash-forecasting

- Health state: unhealthy (failing streak 5)
- Probe declared in: image (backend/services/Dockerfile.service)
- Effective test: CMD-SHELL python -c "import os,urllib.request,sys;…/health…"
- Executable: python — present (`which python` → /usr/local/bin/python, exit 0)
- Last probe exit code: 1
- Last probe output: <verbatim, including traceback>
- Manual replay: exit 1 in 0.31s — <verbatim>
- Attribution: <failing element of the definition, or blocking condition>
```

`Attribution` is never empty for a non-healthy container. That invariant is Property 1.

The classifier that produces `Attribution` is a pure function from the captured JSON to record entries, and lives apart from the collector that shells out to Docker. That separation is what makes the diagnosis logic unit-testable with fixture JSON and no daemon.

## Component 2: Deployment Verification Check (Requirements 2, 8.6)

`scripts/verify/deployment_check.py --env {production|staging}`. One check, two environment tables, identical rules — which is how 8.6 is satisfied by construction rather than by a parallel implementation that could drift.

```python
ENVIRONMENTS = {
    "production": [
        Endpoint("https://kailash-ai.in/",              {200},           content_type="text/html"),
        Endpoint("https://www.kailash-ai.in/",          {200, 301, 308}),
        Endpoint("https://api.kailash-ai.in/api/health", {200}),
    ],
    "staging": [
        Endpoint("https://staging.kailash-ai.in/",              {200}, content_type="text/html"),
        Endpoint("https://www.staging.kailash-ai.in/",          {200, 301, 308}),
        Endpoint("https://staging-api.kailash-ai.in/api/health", {200}),
    ],
}
```

Rules:

1. **Status and content type** (2.1–2.3, 2.7). Redirects are not followed, because following them would let a 301 to an unrelated host pass as 200. Every out-of-set status is reported with its URL and observed code.
2. **Asset manifest agreement** (2.4). Parse the served HTML for `src`/`href` values matching the CRA hashed pattern `\.[0-9a-f]{8,}\.(js|css)`, and require that set to be contained in `asset-manifest.json` from the deploying build. Containment, not equality: the manifest legitimately lists assets the entry HTML does not reference (lazy chunks, source maps). Requiring equality would fail on every code-split build. In CI the manifest comes from the build artifact in the same run; run manually, from `--manifest`.
3. **Certificate margin** (2.5). `ssl.SSLSocket.getpeercert()['notAfter']`, parsed and compared to now + 14 days, per hostname. Reported as days remaining so the output is useful before it is failing.

Placement (2.6): a `verify` job in each deploy workflow, `needs` the deploy job, running the check against the environment just deployed. Its exit code is the job's exit code, which is what "record the exit code in the workflow run" means in GitHub Actions terms.

Network handling: a DNS or connection failure is exit 2, not 1. A green pipeline that went red because the runner lost egress is a different event from production being down, and conflating them trains people to ignore the check.

## Component 3: Config Drift Check (Requirement 3)

`scripts/verify/config_drift.py`. Rule-based; each rule declares extractors and an agreement test.

### Rule `firebase-project-id` (3.1, 3.7)

| Path | Extractor |
| --- | --- |
| `frontend/.firebaserc` | JSON, `.projects.default` |
| `frontend/.env.production` | dotenv key matching `*FIREBASE_PROJECT_ID*` |
| `.github/workflows/deploy-frontend.yml` | YAML, `projectId` under the hosting-deploy step |
| `backend/.env.example` | dotenv `FIREBASE_PROJECT_ID` |

Exit 0 only when all four are present and identical. A **missing** declaration is a finding, not a skip. Skipping absent values would let the check pass by deleting a line — the check would then certify agreement among three files while the fourth silently targets nothing.

### Rule `github-repo-slug` (3.2)

Scan every tracked file for `(?:github\.com[:/])(?P<owner>[\w.-]+)/(?P<name>kailash)(?:\.git)?\b`, plus the bare `owner/kailash` form. Every match must be `urgaa-eka/kailash`. `deploy/vultr/deploy.sh` is additionally declared a **required source** — it must yield at least one match — because that script runs `git reset --hard`, `git clean -fd` and `git clone` against whatever it resolves, and a vacuous pass there is the most dangerous outcome in the whole check.

### Rule `firebase-app-identity` (3.3)

A Firebase project *id* (`kailash-29111`) and project *number* (`794735482892`) are unrelated strings; no string operation derives one from the other. Two comparisons instead:

1. `appId.split(":")[1]` must equal `messagingSenderId` in `frontend/src/lib/firebase.js`. The Firebase SDK config always carries the project number in both, so this catches a partial copy-paste from another project using only in-repository evidence.
2. `appId.split(":")[1]` must equal `data/project_map.json[project_id]`. The map is a small reviewed file recording the one-time console lookup, `{"kailash-29111": "794735482892"}`. Adding an environment means adding a line and a reviewer noticing.

Note that rule 1 alone would have passed the pre-correction config: `kailash-38268`'s `appId` and `messagingSenderId` agreed with each other perfectly. Both were internally consistent and pointed at the wrong project. Only rule 2, or evidence from outside the repository, catches that.

### Rule `node-version` (beyond the letter of Requirement 3)

The same defect class, currently live: `ci.yml`'s frontend job pins Node 18, `deploy-frontend.yml` pins 20, `frontend/Dockerfile` uses `node:20-alpine`, the developer host runs 24. CI is therefore validating a build on a runtime no deployment uses. The rule requires the CI frontend job and the deploy workflow to agree, taking the deployed version (20) as authoritative. Flagged as an extension so review can drop it without touching 3.1–3.3.

### Placement

- New `config-drift` job in `ci.yml`, triggered on pull request and push to main (3.4).
- Both deploy workflows gain a `preflight` job running drift, secret scan and repo state, which every deployment job `needs` (3.6). Covered by Component 10.
- 3.5 — exit 0 on current `main` — is a test case, not a code path: `tests/verify/test_config_drift.py::test_passes_on_real_repository`.

## Component 4: Secret Scan and Credential Handling (Requirement 4)

### Compose changes (4.1, 4.2)

```yaml
# before
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-kailash_prod_2026}  <!-- secret-scan: allow documents the credential incident being remediated -->
# after
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?POSTGRES_PASSWORD must be set}
```

Compose's `:?` form aborts during configuration parsing, before any container is created. That is precisely what 4.2 requires — non-zero exit "before any Data_Services container accepts a network connection" — and it is stronger than a runtime guard, which would need a container to exist first. Applies to `POSTGRES_PASSWORD` and `REDIS_PASSWORD` at all four occurrence sites: `postgres.environment`, `redis.command`, `backend.environment` (`REDIS_URL`, `POSTGRES_URL`), and `company.environment` (`COMPANY_DB_URL`).

Consequence to plan for: `:?` makes *every* compose subcommand require the variables, including `docker compose config` and `build`. The CI `compose-build` job must export throwaway values, and `docs/DEPLOYMENT.md` must state the variables as a hard precondition. This is a deliberate trade — the failure moves from "silently deployed with a published default password" to "loud failure at parse time".

`PLATFORM_INTERNAL_TOKEN` also gets `:?`. It currently defaults to empty, and `require_internal_token` comparing an empty expected token against an absent header is an authentication bypass waiting for a caller who omits the header. Flagged as beyond the letter of 4.1, and worth doing in the same edit.

### Scanner design (4.3, 4.5, 4.7)

Corpus: `git ls-files -z` under `--root`. Untracked files are out of scope by definition — 4.3 says "every file tracked by git".

Detectors, in order:

1. **Denylist** — literals from `data/denylist.txt`, seeded with `kailash_prod_2026` and `kailash_redis_2026`. Applied to every file including lockfiles. Rotation never adds the *new* value here; a denylist of live credentials would itself be the leak.  <!-- secret-scan: allow documents the credential incident being remediated -->
2. **Structured patterns** — `-----BEGIN [A-Z ]*PRIVATE KEY-----`, `AIza[0-9A-Za-z_\-]{35}`, `gh[pousr]_[A-Za-z0-9]{36,}`, `AKIA[0-9A-Z]{16}`, `xox[baprs]-`, and `"type"\s*:\s*"service_account"`.
3. **Assignment heuristic** — a key matching `(PASSWORD|SECRET|TOKEN|API_?KEY|PRIVATE_KEY|CREDENTIAL)` assigned a value that is not a placeholder, not an environment reference (`${…}`, `os.environ`, `secrets.`, `vars.`), and not shorter than 8 characters.
4. **Compose strictness** — the `:?`-not-`:-` rule from above, expressed as a scanner rule so a reverted default is caught by the same job.

**Placeholder exemption** (4.5) requires *both* conditions: the path matches `*.env.example` **and** the value matches the placeholder grammar `""`, `changeme`, `CHANGE_ME`, `REPLACE_ME`, `<…>`, `your-*`, `xxx*`, `***`. A real credential in `.env.example` is still a finding, and a placeholder anywhere else is still reported — which is exactly how "limited to files matching `*.env.example`, verified by the Secret_Scan reporting no other path" is verified.

**Suppression**: `# secret-scan: allow <reason>` on the same or preceding line. Suppressions are counted and printed **even on success**, so a growing suppression list is visible rather than a silent path to a green check.

Encoding: files that are not valid UTF-8 are skipped and counted. Lockfiles are exempt from detectors 2 and 3 (integrity hashes trip entropy heuristics) but never from the denylist.

### Rotation (4.6)

Rotation is an operator action, documented in `docs/runbooks/staging.md` alongside the credential model: generate, store in the GitHub environment secret, update the VPS `.env`, `docker compose up -d` the affected services, verify `/api/health`. The design contribution is the ordering — Postgres password rotation requires `ALTER ROLE` inside the running database before the compose value changes, or the backend cannot reconnect. Rehearsed on staging first, which is a concrete reason staging exists.

## Component 5: Buildable Build Definitions (Requirement 5)

### What is dead

The nine `backend/services/<service>/Dockerfile` files copy from `platform/` and `services/<service>/`, neither of which exists post-consolidation. Compose builds all nine services from `backend/services/Dockerfile.service` with `SERVICE` and `PORT` args. The nine files are unreferenced and unbuildable.

**Remove them** rather than update them. Requirement 5.3 permits either, but two definitions of the same image is drift by construction — the exact class Requirement 3 exists to eliminate. `Dockerfile.service` is the single definition; a corrected per-service copy would be a second one waiting to disagree.

`backend/services/company/Dockerfile` stays. It uses current paths (`/srv`, `backend.services.company.app.main`) and compose references it.

### `build_audit.py` (5.2, 5.3, 5.5)

Static, no daemon, so it runs on every push:

1. Enumerate tracked `Dockerfile*` under `backend/` and the root.
2. For each, find the compose service referencing it, and take that service's `context` and `args`.
3. Parse `COPY` and `ADD` source operands, substituting declared `ARG` values.
4. Assert each source resolves inside the context. Report build file plus missing path (5.5).
5. A tracked build file that no compose service references and whose paths do not resolve is a finding — so a reintroduced dead Dockerfile fails CI.

Argument substitution is why this is worth writing rather than relying on the real build: `COPY backend/services/${SERVICE}/requirements.txt` only resolves for the nine known `SERVICE` values, and the audit checks all nine in milliseconds where nine real builds take minutes.

### CI changes (5.1, 5.4)

`compose-build` currently runs `docker compose -f docker-compose.yml build --pull` with **no `--profile`**. Profile-gated services are inert without it, so the nine Platform_Services, `company` and `frontend` are not built in CI today — 5.1 and 5.4 are unverified, not satisfied. Corrected job:

```yaml
compose-build:
  name: Compose build (sanity)
  runs-on: ubuntu-latest
  env:
    POSTGRES_PASSWORD: ci-throwaway
    REDIS_PASSWORD: ci-throwaway
    PLATFORM_INTERNAL_TOKEN: ci-throwaway
  steps:
    - uses: actions/checkout@v4
    - run: python -m scripts.verify.build_audit
    - run: docker compose --profile kailash-ai -f docker-compose.yml build --pull
```

The static audit runs first: it fails in seconds on a path error that would otherwise surface minutes into a layer build.

## Component 6: Rollback (Requirement 6)

### Frontend (6.2, 6.3)

Firebase Hosting keeps release history; rollback is a pointer switch, not a rebuild.

```bash
# list releases, newest first
firebase hosting:releases:list --project kailash-38268
# roll live back to a named version
firebase hosting:clone kailash-38268:live@<VERSION_ID> kailash-38268:live
```

One substitutable token, `<VERSION_ID>`, which is what 6.1 means by "executable without modification apart from a version identifier". Propagation is seconds to a couple of minutes, comfortably inside the 10-minute bound in 6.3. Verified by `deployment_check.py --env production --manifest <target-release-manifest>`.

### Backend (6.4, 6.5, 6.6)

Today `deploy.sh` rebuilds from git HEAD, so there is nothing to roll back *to* — only something to rebuild. Two changes make a real rollback possible.

**Tag by commit.** `deploy-backend.yml` passes `GIT_COMMIT` as a build arg and tags the image `kailash-backend:<sha>` in addition to `:latest`, retaining the last 10 tags. Compose gains an `image:` key alongside `build:` so a prior tag can run without a rebuild:

```yaml
backend:
  image: kailash-backend:${BACKEND_IMAGE_TAG:-latest}
  build:
    context: .
    dockerfile: Dockerfile
    args:
      GIT_COMMIT: ${GIT_COMMIT:-unknown}
```

Rollback becomes:

```bash
BACKEND_IMAGE_TAG=<COMMIT_SHA> docker compose -f docker-compose.yml up -d --no-build backend
```

This edits `docker-compose.yml`, a Deployment_Critical_Path, so Requirement 9.4's confirmation applies.

**Report the commit** (6.6). `GIT_COMMIT` becomes an `ENV` in the root `Dockerfile`; `HealthResponse` in `backend/shared` gains an optional `commit` field; the health handler populates it from `os.environ.get("GIT_COMMIT", "unknown")`. This is the one additive application change in the design, and it exists because 6.6 requires the health body to identify what is actually running — the single most useful fact during an incident.

### Precondition check (6.8)

`rollback.py --target <id> --env <env> --check` resolves the identifier against Firebase release history and local image tags, exits non-zero printing the requested identifier when absent.

Deliberately a *checker*, not an automation wrapper. Requirement 6.1 wants documented commands an operator runs; an operator mid-incident should execute commands they can read, not trust a script to orchestrate a rollback. The script answers "does this target exist" — the question that is tedious and error-prone to answer by hand — and stops there.

### Rehearsal (6.7)

Rehearsed against staging, timed, recorded in `docs/records/rollback-rehearsal.md`. Rehearsing on production would mean deliberately serving a stale release to users to prove we can serve a stale release.

## Component 7: Docker Host Cleanup (Requirement 7)

### Accountability model

A container is accounted for when either:

- its `com.docker.compose.project.config_files` label resolves to a compose file tracked in this repository, or
- its name appears in `scripts/verify/data/retained_containers.json`.

Anything else is unaccounted: exit 1, printing name and image (7.6).

Label-based ownership rather than name matching, because names are cosmetic and a container named `kailash-backend` started by hand from an unrelated compose file is not the same thing as the stack's backend.

### Retained list as source of truth

```json
{
  "retained": [
    {
      "name": "mcp-tunnel-cloudflared-1",
      "image": "cloudflare/cloudflared:latest",
      "owner": "docs/guides/docker-and-mcp.md — Docker MCP tunnel",
      "published_ports": [],
      "justification": "…",
      "reviewed": "YYYY-MM-DD"
    }
  ]
}
```

`docs/records/docker-host-cleanup.md` is **generated** from this file by `orphan_review.py --emit-record`. One source, one derived document — a hand-written record plus a machine-read list is two sources that will disagree.

`published_ports` records port and bind address for every retained container that publishes one (7.5), which is the field that makes "what is listening on this box" answerable.

### Classification, not prejudgement

The six named containers are classified during execution, from evidence: labels, image, `Created`, `Command`, published ports, and whether any repository documentation claims them. The design specifies the procedure and the record schema. It does not pre-decide — `mcp-tunnel-*` plausibly belongs to the documented Docker MCP tunnel, and `nervous_dhawan`, `interesting_northcutt`, `gifted_leavitt` carry Docker-generated names that suggest ad-hoc `docker run`, but "suggests" is not evidence and `docker rm` is not reversible.

### Confirmation gate (7.3)

```python
def remove(candidates, *, confirmed: bool, execute) -> list[str]:
    if not confirmed:
        return []                       # no destructive command issued
    return [execute("docker", "rm", "-f", c) for c in candidates]
```

`execute` is injected. In tests it records calls, which is how "no `docker rm` without confirmation" is verified without a Docker daemon and without removing anything. Confirmation is per-run and explicit; `--yes` alone is insufficient, the run must also name the containers it intends to remove so a stale `--yes` cannot remove something added since.

## Component 8: Staging Environment (Requirement 8)

### Frontend: options

**Option A — named Firebase preview channel on `kailash-38268`.**
Stable hostname `https://kailash-38268--staging.web.app` (named channels keep a fixed URL; only unnamed ones get hash suffixes). No new project, no new service account, no new config values fanned out across files. `frontend/package.json` already has a `firebase:preview` script. Trade-off: staging and production share the Firebase project, therefore share Auth configuration, Firestore rules, API key restrictions and hosting release history. An Auth configuration change cannot be validated on staging.

**Option B — second Firebase project.**
Full isolation: own hosting site, own web app, own `appId`, own service account, naturally distinct secret names for 8.3. Trade-off: the Firebase project identifier stops being a single global value, so `config_drift.py` must become environment-aware, and a second project needs ongoing configuration parity — the drift surface Requirement 3 exists to shrink.

**Recommendation: Option A.** Requirement 8.1 asks only for a distinct hostname, and a named channel provides one today at zero infrastructure cost. The isolation that matters for a promotion gate is *backend and data* isolation, which the compose recommendation below provides regardless of which frontend option is chosen. Option B buys Firebase-project isolation at the cost of doubling the configuration surface — which is the defect class this spec is trying to close. Accepted limitation, recorded in `docs/runbooks/staging.md`: Firebase Auth and Firestore rule changes are not validated by staging. Revisit if those begin to change.

Channel expiry is set to 30 days and refreshed on every staging deploy, so an abandoned staging URL expires rather than silently serving an ancient build.

### Backend: options

**Option C — second VPS.**
Separate kernel, daemon, ports, TLS and blast radius. A staging build cannot starve production. Costs another instance, another DNS record, another certbot lifecycle, and doubles patching.

**Option D — second compose project on the same host.**
`docker compose -p kailash-staging --profile kailash-ai --env-file .env.staging up -d` with a port offset and an overlay file. Compose namespaces volumes by project, so `kailash-staging_postgres_data` is created fresh. No new instance, no new DNS beyond one A record already pointing at the box, nginx routes `staging-api.kailash-ai.in` to the offset port. Trade-off: shares CPU, memory, disk and the Docker daemon with production. A staging build competes with production for resources, and a careless `docker system prune` hits both.

**Recommendation: Option D, with hard resource ceilings — conditional on the Requirement 1 outcome.**

Option D satisfies every criterion in Requirement 8: the same 15 containers (8.2, same compose file and profile), a distinct hostname (8.1, via nginx and certbot), distinct secret names (8.3, via `.env.staging` and `STAGING_*` GitHub secrets). It exists without provisioning, which means staging can be in place before the next deploy rather than after the next procurement.

The resource-contention risk is mitigated explicitly, not hoped away:

```yaml
# deploy/staging/docker-compose.staging.yml — overlay, applied on top of docker-compose.yml
services:
  backend:
    ports: ["127.0.0.1:9000:8000"]
    deploy:
      resources:
        limits: { cpus: "0.50", memory: 512M }
  # …one entry per service: port offset +1000, limits declared
```

**The recommendation is conditional.** If the Requirement 1 diagnosis confirms hypothesis H1 — that the host is resource-saturated and that is why fourteen probes are timing out — then Option D adds a second full stack to a host that cannot sustain one, and the recommendation flips to Option C. Requirement 1 must be diagnosed before Requirement 8 is built. That ordering is a real dependency, not a preference, and the tasks phase needs to honour it.

### Data bootstrap on fresh staging volumes

`database/postgres_init.sql` (pgcrypto, uuid-ossp) and `database/mongodb_init.js` (collections, indexes) run only via `docker-entrypoint-initdb.d` on an **empty** data directory. Production's volumes have long since been initialised, so those scripts have not run there since the first boot.

Staging's volumes are new, so staging becomes the only environment that exercises the first-boot provisioning path. Two consequences:

- Genuinely valuable: a broken init script currently fails only during disaster recovery, the worst possible moment to discover it. Staging surfaces it on an ordinary Tuesday.
- Expect an early divergence finding: any schema, index or extension applied to production by hand and never added to the init scripts will be absent from staging. That gap is a defect the init scripts should absorb, and finding it is a benefit of this design, not a problem with it.

Staging receives **no copy of production data.** Seeding, if it is ever needed, is a separate decision with its own privacy consequences. Out of scope here.

| Production | Staging |
| --- | --- |
| `POSTGRES_PASSWORD` | `STAGING_POSTGRES_PASSWORD` |
| `REDIS_PASSWORD` | `STAGING_REDIS_PASSWORD` |
| `PLATFORM_INTERNAL_TOKEN` | `STAGING_PLATFORM_INTERNAL_TOKEN` |

Disjoint name sets, verifiable by reading the workflow `env:` blocks — which is exactly the verification 8.3 specifies. GitHub Environments `staging` and `production` carry them, so the production environment can additionally require a reviewer.

## Component 9: Repository State Integrity (Requirement 9)

### Working-tree gate (9.1, 9.6)

```python
CRITICAL_PATHS = ("deploy/", ".github/workflows/",
                  "frontend/.firebaserc", "frontend/.env.production",
                  "docker-compose.yml")
```

`git status --porcelain -- <path>` per path; any output is a finding naming the modified path. Handles rename entries (`R  old -> new`, both sides checked) and quoted paths with spaces. Prefix matching is path-segment aware: `deploy/` must not match a hypothetical `deployment-notes.md`.

Honest note on placement: inside GitHub Actions this check is near-vacuous, because `actions/checkout` always produces a clean tree. Its load-bearing placements are (a) locally, before an operator runs a deploy by hand, and (b) **on the VPS inside `deploy.sh` after `git reset --hard`**, where a reported modification means somebody edited files on the production server. It stays in CI as defence in depth and as the enforcement point branch protection can require, but the VPS placement is where it earns its keep.

### Destructive-operation guard (9.3)

`deploy.sh` runs `git reset --hard`, `git clean -fd` and `git clone` against `$APP_DIR`. `git clean -fd` in the wrong directory destroys untracked files with no recovery. Guard before any of the three:

```bash
assert_expected_checkout() {
    local dir="$1" expected="urgaa-eka/kailash"
    git -C "$dir" rev-parse --is-inside-work-tree >/dev/null 2>&1 || {
        echo "FATAL: ${dir} is not a git work tree; refusing destructive git operation" >&2
        exit 1
    }
    local slug
    slug="$(git -C "$dir" remote get-url origin | sed -E 's#(git@|https://)github\.com[:/]##; s#\.git$##')"
    [ "$slug" = "$expected" ] || {
        echo "FATAL: ${dir} origin is '${slug}', expected '${expected}'" >&2
        exit 1
    }
}
```

The `sed` normalisation must map `git@github.com:urgaa-eka/kailash.git`, `https://github.com/urgaa-eka/kailash.git` and `https://github.com/urgaa-eka/kailash` to the same slug. That normalisation is Property 18, and it is worth a property test because a normaliser that silently returns the unmodified URL makes the guard reject every valid checkout — turning a safety feature into an outage.

The clone branch needs a second guard: currently, if `$APP_DIR` exists non-empty without `.git`, `git clone` fails after the script has already run `install_prerequisites`. Assert the directory is absent or empty before cloning.

### Commit confirmation (9.4)

A local `pre-commit` hook: when staged paths intersect `CRITICAL_PATHS`, fail with a message instructing the operator to re-run with `CONFIRM_CRITICAL_PATH=1` in the environment.

An environment token rather than an interactive prompt because pre-commit hooks have no reliable TTY — from an IDE's git integration a prompt hangs or silently fails, and a safety gate that hangs gets disabled. Setting a variable is a deliberate, auditable act with the same intent and none of the fragility.

Stated plainly: any local hook is bypassable with `--no-verify`. The unbypassable enforcement is the CI `preflight` job plus branch protection. The hook exists to catch the accidental case, which is the common one.

### Deployed SHA recording (9.5)

Both deploy workflows write `github.sha` to `$GITHUB_STEP_SUMMARY` and pass it as the `GIT_COMMIT` build arg, tying 9.5 to 6.4 and 6.6 — one commit identity that appears in the workflow run, the image tag, and the health response.

## Component 10: Workflow Topology (Requirements 2.6, 3.4, 3.6, 4.4, 8.4, 8.5, 8.7, 8.8)

### Target graph

```
push to main
  │
  ├─ ci.yml  (workflow_call + push + pull_request)
  │    lint · shared · services×9 · company-service · company-infra ·
  │    backend · frontend · compose-build · config-drift · secret-scan ·
  │    verify-scripts
  │
  └─ deploy-{frontend,backend}.yml
       preflight        (config-drift, secret-scan, repo-state)
         └─ ci-gate     (uses: ./.github/workflows/ci.yml)
              └─ deploy-staging
                   └─ verify-staging   (deployment_check.py --env staging)
                        └─ deploy-production
                             └─ verify-production
```

`deploy-production` transitively requires `preflight`, `ci-gate`, `deploy-staging` and `verify-staging`. GitHub Actions skips a job whose `needs` failed, so a failure anywhere upstream terminates the run before any deployment command executes — satisfying 3.6, 8.7 and 8.8 through the dependency graph rather than through in-job conditionals that can be forgotten on the next job added.

### Two existing conditions block 8.8

**Failure masking.** `ci.yml`'s `backend` job ends `pytest … -q || true`, and its `frontend` job runs `yarn build || true`. Both jobs are therefore incapable of failing, so they cannot gate anything. `deploy-backend.yml`'s `test` job has the same `|| true`. Requirement 8.8 is unsatisfiable while these remain.

Removing them is required, and the consequence should be planned for rather than discovered: **CI may go red immediately.** The `|| true` was presumably added because something failed. Finding out what is part of the work, and the tasks phase likely has to sequence it early, because no other gate in this design means anything while a gating job cannot fail.

**No linkage.** `ci.yml` and the deploy workflows are independent, separately triggered workflows today — a deploy does not wait for CI. Fix: add `workflow_call` to `ci.yml`'s triggers and have each deploy workflow invoke it as the `ci-gate` job.

### `workflow_gate.py`

Rather than trusting the YAML to stay correct, `scripts/verify/workflow_gate.py` parses `.github/workflows/*.yml` and asserts:

1. Every job containing a deployment command (`firebase … deploy`, `hosting:clone`, `action-hosting-deploy`, `ssh-action`, `docker compose … up`) has `preflight`, `ci-gate`, `deploy-staging` and `verify-staging` as transitive `needs`.
2. Every production deployment job is preceded by the corresponding staging job (8.4, 8.5).
3. No job in the gating set contains a step whose `run` masks failure (`|| true`, `continue-on-error: true`, `exit 0` tail).
4. A verification job follows each deployment job (2.6).

Graph reachability over parsed YAML, no network, runs in the `config-drift` job. This is what makes 8.8 a checked property instead of a review habit.

## Error Handling

| Condition | Handling | Exit |
| --- | --- | --- |
| Docker daemon unreachable | Report the daemon as unavailable; classify nothing | 2 |
| `git` absent or `--root` not a repository | Report; do not fall back to filesystem walk | 2 |
| DNS/TLS/connection failure during verification | Report per endpoint with the exception type | 2 |
| Malformed JSON/YAML in a scanned file | Finding against that file, continue scanning others | 1 |
| File not valid UTF-8 | Skip, count, report the count in the summary | unchanged |
| Expected config file missing | Finding — absence is drift, not a skip | 1 |
| `docker exec` fails while replaying a probe | Record verbatim as evidence, do not raise | 1 |
| Rollback target absent | Print requested identifier | 1 |

Two rules run through all of it. **A check never crashes with a traceback**, because an unhandled exception is indistinguishable from a check that was never wired up. And **a check never passes because it could not look** — every absent input is either a finding (1) or unavailability (2), never silence.

## Toolchain: the yarn inconsistency

Facts: `frontend/package.json` declares `packageManager: yarn@1.22.22`; `frontend/yarn.lock` exists and CI caches it; `frontend/Dockerfile` runs `yarn install --frozen-lockfile`; `deploy-frontend.yml` runs `yarn install` and `yarn build`. The developer host has Node 24 and npm 11 and **no `yarn` on `PATH`**, so no documented frontend command runs locally.

**Option 1 — standardise on npm.** Delete `yarn.lock`, generate `package-lock.json`, rewrite the scripts, the Dockerfile and two workflows. npm resolves the tree independently, so the lockfile it produces is not guaranteed to match the tree production runs today. That is a dependency-tree change wearing a tooling change's clothing, landing inside a Deployment_Critical_Path, during a production-readiness effort.

**Option 2 — keep yarn, make it available locally.**

```
corepack enable
corepack prepare yarn@1.22.22 --activate
```

Corepack ships with Node 24, reads the `packageManager` field, requires no global install and no repository change, and makes the local machine match CI and the Dockerfile exactly.

**Recommendation: Option 2.** The lockfile determines what production runs; regenerating it to fix a `PATH` problem changes the deployed artifact to solve a workstation issue. Corepack closes the gap with two commands. Added to `CONTRIBUTING.md` as a prerequisite.

Two supporting decisions:

- **The verification checks never invoke `yarn` or `node`.** Pure Python, so verification works on a machine where the frontend toolchain is absent or broken. A gate that depends on the thing it gates is not a gate.
- **Pin CI's frontend Node to 20**, matching `deploy-frontend.yml` and the Dockerfile. CI currently validates on 18 while deploying on 20; the version that ships is the version of record. Enforced by the `node-version` drift rule.

## Testing Strategy

Verification code that is wrong is worse than no verification code, because it produces confident green output. Every check is therefore tested, and the design is shaped to make that possible.

### The structural decision: pure classifier, thin collector

Each Docker- or network-touching check splits in two:

- a **collector** that shells out or makes requests and returns plain data (dicts, dataclasses)
- a **classifier** that is a pure function from that data to `list[Finding]`

All rule logic lives in the classifier. It is unit- and property-tested with fixture data and no daemon, no network, no repository state. The collector is a thin adapter covered by a handful of `@pytest.mark.docker` / `@pytest.mark.network` tests that skip when the prerequisite is absent.

This split is why the Requirement 1 diagnosis logic is testable at all — the classifier consumes `docker inspect` JSON from a file, so all fourteen failure shapes can be exercised without reproducing them.

### Layout

```
tests/verify/
  conftest.py              tmp-repo fixture (git init + synthetic files), fake executor,
                           local http.server fixture, docker/network skip markers
  test_common.py
  test_health_diagnose.py
  test_deployment_check.py
  test_config_drift.py
  test_secret_scan.py
  test_build_audit.py
  test_rollback.py
  test_orphan_review.py
  test_repo_state.py
  test_workflow_gate.py
  test_properties.py       Hypothesis properties, ≥100 examples each
  fixtures/
    inspect_*.json         captured docker inspect shapes, including malformed
    workflows/*.yml        synthetic workflow graphs
```

### Per-check approach

| Check | How it is tested |
| --- | --- |
| `config_drift.py` | Synthetic repo in `tmp_path` with the four files written to chosen values. One fixture per rule that must exit 0, one that must exit 1 with the path and value asserted in stdout. Plus `--root` = real repository asserting exit 0 (3.5). |
| `secret_scan.py` | Corpora seeded with each detector's pattern at known line numbers; assert the reported line number is exact. Near-miss corpora (a password-shaped variable assigned `${VAR}`) must not fire. Placeholder matrix over path × value. |
| `deployment_check.py` | `http.server` on an ephemeral port returning scripted statuses, content types and HTML bodies. Certificate logic tested against synthesised `notAfter` values, not live certificates. Live production requests are a separate smoke invocation, never a unit test. |
| `health_diagnose.py` | Classifier fed `fixtures/inspect_*.json` covering: 200-but-unhealthy (1.7), executable absent (1.2), replay-succeeds-probe-fails (1.6), connection refused, `HTTPError` traceback, no healthcheck declared (frontend), and truncated/malformed inspect output. Record generation asserted for entry completeness. |
| `build_audit.py` | Synthetic contexts and Dockerfile bodies with argument-templated `COPY` paths; assert every one of the nine `SERVICE` values resolves, and that a deliberately reintroduced `COPY platform /opt/platform` is reported with its build file. |
| `orphan_review.py` | Container lists as fixtures; recording fake executor asserts zero `docker rm` calls without confirmation and exactly the named ones with it. |
| `repo_state.py` | Synthetic `git status --porcelain` outputs: renames, quoted paths with spaces, staged vs unstaged, and prefix collisions (`deployment-notes.md` must not match `deploy/`). URL normalisation across ssh/https/`.git` forms. |
| `workflow_gate.py` | Synthetic workflow graphs: missing `needs`, a masked gating job, production before staging, a deploy job with no verification successor. Plus an assertion against the real workflow files. |
| `rollback.py` | Available-set fixtures with present, absent, and near-miss identifiers. |

### Property tests

`hypothesis` is not currently a dependency. Add a `requirements-dev.txt` pinning `hypothesis` and `pytest`, installed by the `verify-scripts` CI job. Properties live in `tests/verify/test_properties.py`, run at ≥100 examples, and each is tagged with its design property:

```python
# Feature: production-readiness, Property 7: For any assignment of a tracked
# configuration value across the files that declare it, the Config_Drift_Check
# exits 0 iff every declared value is present and identical to the expected value.
@given(values=st.lists(st.one_of(st.just(None), project_ids()), min_size=4, max_size=4))
@settings(max_examples=200)
def test_drift_agreement(tmp_repo, values):
    write_project_ids(tmp_repo, values)
    report = config_drift.check(root=tmp_repo)
    expected_ok = all(v is not None for v in values) and len(set(values)) == 1
    assert (report.exit_code() == Exit.OK) == expected_ok
    if not expected_ok:
        printed = render(report)
        for path, value in declared(tmp_repo, values):
            assert path in printed and (value is None or value in printed)
```

Generators worth building deliberately, since they carry the edge cases the prework identified: HTTP status codes across and outside allowed sets; `notAfter` timestamps straddling the 14-day boundary; commit SHAs in full, short and mixed case; git remote URLs in every form; file paths with spaces, unicode and prefix collisions; credential-shaped strings and their placeholder near-misses; workflow graphs including cycles and orphan jobs.

### Integration and smoke tests

Marked and skipped when the prerequisite is absent, so the unit suite runs anywhere:

- `@pytest.mark.docker` — the 15 `which` probes (1.2), the nine service health requests (1.4), the 180-second full-stack health assertion (1.5), compose failing on unset credentials (4.2).
- `@pytest.mark.network` — live production and staging endpoint checks (2.1–2.3, 4.6, 8.6).
- Document assertions (5.6, 6.1, 7.1) are ordinary fast tests: they read repository files and assert required content is present.

### CI placement

New `verify-scripts` job runs `pytest -q tests/verify` (excluding docker/network marks) on every push and pull request, and `config-drift`, `secret-scan` and the `preflight` jobs all `needs: verify-scripts`. A check whose own tests fail must not be trusted to gate a deployment.

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Every non-healthy container is attributed

For any set of captured container health observations, the Diagnosis_Record emitted from that capture contains exactly one entry per container not reporting `healthy`, each entry carrying the container name, the effective health check test command, the observed probe exit code, the observed probe output, and a non-empty attribution — including when the container's health path returned 200 and when it remains unhealthy after its definition was corrected.

**Validates: Requirements 1.1, 1.7, 1.8**

### Property 2: Declared start period covers measured startup

For any container with a measured time to first successful probe, the check passes if and only if that container's declared start period is greater than or equal to the measured time.

**Validates: Requirements 1.6**

### Property 3: Probe executable extraction matches invocation

For any health check test in `CMD`, `CMD-SHELL`, or bare-string form, the executable name extracted from it is the executable the container runtime will invoke, and the extraction is unchanged by surrounding whitespace, quoting, or environment references within the test.

**Validates: Requirements 1.2**

### Property 4: Endpoint verification accepts exactly the allowed statuses

For any environment and any mapping from its endpoints to observed HTTP statuses and content types, the Deployment_Verification_Check exits 0 if and only if every observed status lies in that endpoint's allowed set and every declared content-type expectation is met; on any failure, standard output contains each offending URL together with its observed status; and corresponding staging and production endpoints carry identical allowed sets.

**Validates: Requirements 2.1, 2.2, 2.3, 2.7, 8.6**

### Property 5: Served assets are contained in the deployed manifest

For any asset manifest and any served HTML document, the check passes if and only if every hashed asset filename referenced by the HTML appears in the manifest.

**Validates: Requirements 2.4**

### Property 6: Certificate expiry margin

For any certificate expiry timestamp and any verification time, the check passes if and only if the expiry is at least 14 days later than the verification time.

**Validates: Requirements 2.5**

### Property 7: Configuration agreement and full reporting

For any assignment of a tracked configuration value across the files that declare it, the Config_Drift_Check exits 0 if and only if every declared value is present and identical to the expected value, and every required source yields at least one value; on any disagreement, standard output contains every participating file path together with the value found in that file.

**Validates: Requirements 3.1, 3.2, 3.5, 3.7**

### Property 8: Firebase application identity is self-consistent

For any Firebase web application configuration, the check passes if and only if the numeric segment of the `appId` equals both the `messagingSenderId` and the project number mapped to the declared Firebase project identifier.

**Validates: Requirements 3.3**

### Property 9: No deployment is reachable without passing every gate

For any deployment workflow graph, every job that invokes a deployment command has the preflight checks, the CI gate, the staging deployment, and the staging verification as transitive prerequisites; every deployment job is followed by a verification job; and no job in that prerequisite set contains a step that masks a non-zero exit.

**Validates: Requirements 2.6, 3.4, 3.6, 4.4, 8.4, 8.5, 8.7, 8.8**

### Property 10: Credentials are detected and placeholders confined

For any corpus of tracked files, the Secret_Scan exits 0 if and only if no file contains a credential-shaped value, where a credential-shaped value is exempt only when its file path matches `*.env.example` and its value matches the placeholder grammar, and no strict-required compose variable is declared with a default; every finding is printed with its file path and its exact line number.

**Validates: Requirements 4.1, 4.3, 4.5, 4.7**

### Property 11: Build sources resolve inside their build context

For any tracked build file and the build arguments declared for it, every `COPY` and `ADD` source path resolves to a path inside that file's declared build context after argument substitution; any unresolved path is printed together with its build file.

**Validates: Requirements 5.2, 5.3, 5.5**

### Property 12: Deployed commit identity round-trips

For any commit SHA, the image tag derived from that SHA parses back to the same SHA, and a service built with that SHA reports the same SHA in its health response body.

**Validates: Requirements 6.4, 6.6**

### Property 13: Rollback targets are resolved before use

For any requested version identifier and any set of available Firebase releases and image tags, the rollback precondition check exits 0 if and only if the identifier is a member of the available set, and prints the requested identifier whenever it is not.

**Validates: Requirements 6.8**

### Property 14: Every container on the host is accounted for

For any set of containers observed on the Docker_Host, the orphan review exits 0 if and only if every observed container is either a service of the tracked Compose_Stack or listed as retained; every unaccounted container is printed with its name and image; and every retained entry carries a non-empty owner, with a published port and bind address recorded whenever that container publishes a port.

**Validates: Requirements 7.1, 7.2, 7.4, 7.5, 7.6**

### Property 15: Irreversible actions require explicit confirmation

For any set of container removal candidates and for any set of staged files intersecting a Deployment_Critical_Path, no destructive command is issued and no commit is created unless explicit operator confirmation is present for that specific set.

**Validates: Requirements 7.3, 9.4**

### Property 16: Staging and production are isolated by name and identical by shape

For any pair of staging and production configurations, their hostname sets are disjoint under normalisation, their credential secret-name sets are disjoint, and their compose service-name sets are identical.

**Validates: Requirements 8.1, 8.2, 8.3**

### Property 17: Deployment-critical paths are clean at deploy time

For any working-tree status output, the repository-state check exits 0 if and only if no reported path lies under a Deployment_Critical_Path, treating rename entries on both sides and matching only on whole path segments; every offending path is printed.

**Validates: Requirements 9.1, 9.6**

### Property 18: Repository identity normalises consistently before destructive operations

For any git remote URL in ssh, https, or `.git`-suffixed form referring to the same repository, normalisation yields the same owner/name slug, and the destructive-operation guard exits with a non-zero code for any slug other than `urgaa-eka/kailash` and for any target directory that is not a git work tree.

**Validates: Requirements 9.2, 9.3**

## Risks, Technical Debt, Open Questions

### Requirement 1 gates Requirement 8

If the health diagnosis confirms host resource saturation, adding a second compose project to that host is the wrong move and the staging recommendation flips from Option D to Option C. Requirement 1 must be diagnosed before Requirement 8 is built.

### Removing `|| true` will likely turn CI red

Three jobs currently mask failures. They must stop masking for Requirement 8.8 to mean anything, and the masking presumably exists because something fails. Expect to fix real failures before any gate in this design is load-bearing.

### `:?` makes every compose subcommand require credentials

A deliberate trade. `docker compose config`, `build` and `ps` will all require the variables. CI and documentation must set them; a developer who does not will hit a clear error rather than a silent default.

### Pre-existing technical debt: three overlapping design-token systems

Not addressed by this design. Recorded because it is live drift of exactly the class Requirement 3 targets, one layer up in the stack:

- `frontend/tailwind.config.js` defines a Go4Garage palette: `g4g-blue #0A3D62`, `g4g-electric-yellow #FFC312`, `g4g-steel-grey`, `highlight-teal #12CBC4`.
- `frontend/src/index.css` `:root` defines a **different** brand palette in HSL — `--g4g-purple 282 95% 27%`, `--g4g-green 126 34% 37%`, `--g4g-bright-green 147 90% 44%`, `--g4g-orange 24 64% 59%` — and wires the shadcn semantic tokens `--primary`, `--secondary`, `--accent` to the purple/green set.
- `frontend/src/styles/theme.css` defines a **third** set as plain CSS variables: `--color-primary: #0A3D62`, `--color-accent: #FFC312`.

Three systems means the rendered colour depends on which one a given component happened to reference. `Config_Drift_Check` could eventually carry a design-token rule, but resolving the conflict is a visual-design decision requiring a decision about which palette is correct — out of scope here, and it needs the same treatment as the Firebase identifier: one source, checked.

### Open questions

1. **Does the backend serve `/api/health`?** No literal health route exists in `backend/**/*.py`; `build_app()` mounts `/health`. The route's real path must be read from the running app's `openapi.json` during Phase A. If it is not `/api/health`, the route is added rather than the probe retargeted — four requirements and both deploy scripts already depend on that path.
2. **What owns `mcp-tunnel-cloudflared-1` and `mcp-tunnel-mcp-proxy-1`?** Plausibly the documented Docker MCP tunnel, but ownership must come from labels and documentation, not from the name.
3. **Frontend staging channel expiry.** 30 days proposed. If a staging URL is shared externally, expiry becomes a surprise; needs an operator decision recorded in the staging runbook.
4. **Retention depth for backend image tags.** 10 proposed. Bounded by VPS disk, which the Requirement 1 host assessment will quantify.
5. **`docker-compose.override.yml` is auto-merged locally but not in production.** `deploy.sh` and `deploy-backend.yml` both pass `-f docker-compose.yml` explicitly, so the override's loopback database ports exist locally and not in production. Correct as it stands, but it means local and production stacks differ in published ports — worth an explicit note in the deployment guide so nobody "fixes" it by removing the `-f`.
6. **Neither deploy path passes `--profile kailash-ai`.** `deploy.sh` and `deploy-backend.yml` both run `docker compose up -d --build` without the profile, so the nine Platform_Services, `company` and `frontend` are not started by a deploy. Whether production is *intended* to run the profiled services is a question the requirements do not settle, and Requirement 8.2 ("staging runs the same 15 containers") only makes sense once it is answered.
